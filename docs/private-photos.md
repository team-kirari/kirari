# 비공개 사진 저장소와 업로드

## 현재 상태 (2026-11-18)

### 갤러리 API 조회 전환 — 운영 API 연결

갤러리에는 `업로드 → 기존 Worker 접수 → private Actions 이미지 검증·메타데이터 제거 → 공개 목록과 검증 사진을 같은 커밋으로 저장 → Worker /gallery 조회` 경로를 추가했습니다. 2026-11-18 갤러리 Worker(`1f197e94-994b-4cb6-9ae2-309125112950`)와 private 공개 목록·워크플로(`beb698a`)를 반영했습니다. 공개 승인된 갤러리 사진 20장의 목록과 실제 이미지의 HTTP 200 응답을 명령줄로 확인했습니다. 앱은 목록 형식 검사를 통과했습니다. 검증기 소스와 프런트엔드의 최종 배포는 이번 공개 저장소 반영 후 Pages 실행 결과를 확인해야 합니다. 아래의 기존 배포 기록은 이전 운영 버전입니다.

- `photo-pipeline/gallery-manifest.mjs`는 `assets/gallery/`의 SHA-256 이름 PNG/WebP와 유효한 공개 메타데이터만 `public-gallery.json`에 기록합니다. staging·프로필·기타 원본은 목록에 넣지 않습니다. 이미지 해시·헤더와 메타데이터가 잘못되면 이전 목록을 교체하지 않습니다.
- `GET /gallery`는 공개 사진의 ID·형식·제목·태그·앨범·저작권자만 반환합니다. `GET /gallery/<SHA-256>.<webp|png>`는 현재 목록에 있는 사진의 고정 Git blob만 스트리밍합니다. GitHub 토큰·인증 링크·blob SHA는 응답에 포함하지 않습니다. 임의 경로·원본·접수 파일 조회는 허용하지 않습니다.
- 화면은 기존 `VITE_STORY_API_URL`에서 갤러리 주소를 얻습니다. 최초 접속·창 복귀·갤러리 새로고침 때 목록을 조회하며 접수 후에는 10초 간격으로 최대 3분간 확인합니다. 목록이 바뀌면 자동 반영합니다. 검증이 늦어지면 나중에 새로고침할 수 있습니다. 조회 실패 시 오류를 표시하고 기존 화면을 유지합니다. 홈 사진 위젯과 통합 검색도 같은 갤러리 상태를 사용합니다.
- 공용 태그·앨범·저작권자 편집 및 목록 숨김은 기존 Firestore를 유지합니다. 숨김은 사진 접근 차단이나 원본 삭제가 아니며 직접 사진 URL과 기존 Pages 파일·Git 이력·다운로드 사본은 남습니다. 사진 자체를 제공 중단하려면 공개 목록에서 제거해야 합니다. API는 매 요청마다 최신 목록을 확인하며 공용 캐시를 사용하지 않습니다.
- 갤러리 사진 추가는 Pages 재배포를 요청하지 않도록 private 워크플로 템플릿을 변경했습니다. 프로필·홈 이미지의 정적 파일 변경은 재배포 경로를 유지합니다. 이미지 디코딩·검증을 수행하는 Actions 시간과 GitHub API 지연은 남습니다. 무료 무제한을 보장하지 않으며 이미지 요청도 Worker·GitHub API 사용량에 포함됩니다.

운영 반영 순서: public 저장소에 검증기와 앱 코드를 반영 → private 저장소의 `.github/workflows/publish.yml`에 `config/private-photos/publish.yml` 반영 → private 파이프라인을 한 번 실행해 공개 목록 생성 → 이야기 Worker 업데이트 → 프런트엔드 Pages를 한 번 배포합니다. 이후 갤러리 업로드마다 Pages를 다시 배포할 필요는 없습니다. 기존 개인 글이나 비공개 원본을 새로 공개하는 작업은 포함하지 않습니다.

화면 확인은 사용자에게 남습니다. 관리자 업로드 후 접수 안내가 보이고 검증 완료 후 사진·태그·앨범이 표시되는지, 비로그인 창에서도 새 사진이 보이는지, 새로고침·확대·메타데이터 편집·목록 숨김이 동작하는지 확인해야 합니다.

검증: 앱 테스트 173개와 사진 파이프라인 테스트 12개 통과, 타입 검사·린트·프로덕션 빌드·이야기 Worker dry-run 통과. 앱 전체 검사는 최초 sandbox 실행에서 로컬 HTTP 연결과 심볼릭 링크 권한 때문에 3개 실패했으며 제한 밖에서 재실행해 전부 통과했습니다. 공개 목록에서 제외된 사진·잘못된 확장자·경로 탐색·손상 목록·위험한 URL·서버 오류를 mock으로 검증했습니다. 실제 계정 업로드·화면 조작은 이번 변경에서 확인하지 않았습니다. 운영 확인에서 발견한 Workers의 미지원 redirect 옵션을 manual로 변경하고 리디렉션을 거부하는 회귀 테스트를 추가했습니다. [Workers Request 문서](https://developers.cloudflare.com/workers/runtime-apis/request/)를 따릅니다.

### 기존 운영 연결 기록

- 원본 저장소는 `team-kirari/kirari-private`이며 비공개입니다. 공개 승인된 `assets/` 사진을 Pages 빌드에 사용합니다.
- 사진 API를 기존 이야기 Worker의 `https://kirari-stories.papercloud.workers.dev/photos`에 배포했습니다. 기존 서버 전용 `STORY_GITHUB_WRITE_TOKEN`과 Firebase 설정을 사용하며 로컬 Git 인증정보를 서버에 복사하지 않았습니다.
- GitHub Actions의 `VITE_PHOTO_UPLOAD_URL`과 로컬 개발 환경에 위 URL을 연결했습니다. 앱·파이프라인 소스를 main에 반영했고 Pages 배포가 성공했습니다. 운영 번들의 API 주소·저작권자 입력·마스터키 제거를 HTTP로 확인했습니다.
- 마스터키 입력과 서버 마스터키 검사를 제거했습니다. Google 로그인과 활성 `admins/{uid}.enabled`를 서버에서 확인합니다. 일반 로그인 계정에는 업로드를 허용하지 않습니다.
- 저작권자 이름을 사진과 함께 private 저장소에 원자적으로 접수합니다. 검증 후 이름만 별도 JSON으로 공개하며 갤러리에서는 `ⓒ 이름 님`으로 표시합니다. 기존 사진의 EXIF를 저작권자 정보로 자동 사용하지 않습니다.
- 사용자가 `PUBLIC_SITE_DISPATCH_TOKEN`을 직접 등록했고, 관리자가 업로드한 사진·저작권자의 검증 후 공개 사이트 자동 배포를 명시적으로 승인했습니다. private 워크플로가 검토된 템플릿과 같음을 확인한 뒤 `PHOTO_PIPELINE_ENABLED=true`를 설정했습니다. 기존 공개 승인 사진은 55개, 활성화 시 대기 사진은 0개였습니다. 수동 실행한 private 파이프라인은 성공했고 `photos-updated` 요청으로 public Pages 재배포까지 성공했습니다.

## 처리 흐름과 공개 범위

### 갤러리 업로드 개선 — Worker 반영, 사이트·파이프라인 반영 전

- 2026-11-18 사용자 승인으로 현재 업로드 Worker를 배포했습니다(version: `fdd75922-f5b8-42cc-80c5-96f8634d8998`). 기존 운영 서버가 `X-Photo-Metadata`를 허용하지 않아 발생한 `Failed to fetch` 원인을 수정했습니다. 로컬·Pages Origin 모두 OPTIONS 204와 해당 헤더 허용을 명령줄로 확인했습니다. 관련 mock 테스트 9개와 Worker dry-run 빌드를 통과했으며 실제 로그인 업로드는 사용자 확인이 남아 있습니다. 이 배포는 사이트·이미지 파이프라인의 미반영 변경을 배포하지 않습니다.

- 여러 사진을 한 번에 선택하거나 추가할 수 있습니다. 사진별 카드에서 앨범·태그·저작권자를 독립적으로 설정합니다.
- 로컬 수정: 등록 버튼으로 선택한 사진 전체와 사진별 메타데이터를 multipart 요청 한 번으로 보냅니다. Worker는 각 파일을 검사한 뒤 전체를 한 커밋으로 staging에 접수하며 사진 수와 관계없이 검증 파이프라인을 한 번 시작합니다. 브랜치 반영 전 실패하면 전체 묶음을 재시도하고, 응답 유실 후 같은 묶음 재시도는 접수 마커로 중복 커밋을 방지합니다. 선택 취소·창 닫기 시 미리보기 Object URL을 해제합니다.
- 로컬 워크플로 템플릿은 공개 assets 변경이 있을 때만 `photos-updated`를 보냅니다. 위 묶음 처리와 조건 변경은 아직 사이트·Worker·private 워크플로에 배포하지 않았습니다.
- 묶음 처리 검증: 타입 검사·린트·프로덕션 빌드·Worker dry-run, 앱 테스트 107개와 파이프라인 테스트 11개 통과. 1·3·14장 단일 요청, 재시도 중복 방지, 브랜치 충돌 재시도, 손상 파일의 전체 커밋 차단을 mock으로 확인했습니다. 실제 로그인 업로드·화면·운영 Actions 실행은 확인하지 않았습니다.
- 다중 업로드 관련 명령줄 검증: 타입 검사·린트·빌드, 관련 테스트 26개 통과. 실제 다중 선택 화면과 실계정 업로드는 사용자 확인이 남아 있습니다.

- 업로드 창을 화면 중앙 모달로 변경하고 사진 미리보기, 파일명 자동 제목, 태그 추가·삭제, 기존 앨범 선택, 새 앨범 만들기를 추가했습니다. 모바일에서는 미리보기와 입력 영역이 세로로 배치됩니다.
- 등록 위치 선택 없이 갤러리에 등록합니다. 사진 제목 입력과 화면 표시는 제거하고 파일명을 내부 제목으로 사용합니다.
- 앨범은 갤러리 안에서 사진을 분류하는 이름입니다. 새 앨범은 사진과 함께 접수되며 독립적인 빈 앨범은 저장하지 않습니다. 기존 앨범 목록은 현재 갤러리에 표시되는 사진에서 가져옵니다.
- 제목·태그·앨범·저작권자를 `X-Photo-Metadata`로 전송합니다. Worker와 이미지 파이프라인에서 동일한 허용 필드·길이·타입을 검증하고 공개 JSON에 보존합니다. 기존 저작권자 전용 JSON도 읽을 수 있습니다.
- 새 파일의 기본 분류는 공개 JSON에서 읽으며, 기존 Firestore 편집 정보가 있으면 해당 정보를 우선합니다. 동일한 원본이 이미 접수된 경우 기존 접수 정보가 유지됨을 안내합니다.
- Worker 업데이트는 완료했으며 전체 변경의 운영 반영에는 사이트·파이프라인 소스 반영이 필요합니다. 실계정 업로드·브라우저 화면 확인은 수행하지 않았습니다.
- 명령줄 확인: 타입 검사, 린트, 앱 테스트 103개, 이미지 파이프라인 테스트 11개, 프로덕션 빌드 통과. 입력의 HTML·위험 URL은 일반 텍스트로 취급하며 손상·과대 메타데이터와 알 수 없는 필드를 거부하는 테스트를 포함합니다.

아래는 기존 운영 흐름입니다. 위 개선을 반영하면 제목·태그·앨범도 사진과 함께 처리합니다.

`사진 + 저작권자 + 관리자 ID token → Worker /photos → private staging/{target}/{sha256}.json → private Actions 검증 → assets/{target}/{sha256}.webp + .json → Pages 재빌드`

로그인 토큰은 전송할 때만 사용하고 사진 파일·메타데이터·로그에 저장하지 않습니다. Worker는 Firebase 계정 확인 API와 해당 ID token으로 Firestore의 자기 관리자 문서를 조회합니다. Firestore 규칙이 프로젝트·현재 Google 로그인 공급자·자기 문서 접근을 검사합니다. Origin은 Pages 주소와 서버에 명시적으로 설정한 `http://127.0.0.1:5173`만 허용합니다.

로컬 변경에서는 PNG/APNG/JPEG/WebP/GIF를 허용하며 앱·Worker·파이프라인의 파일 용량과 가로·세로·총 픽셀 상한을 제거했습니다. 실제 헤더·MIME와 디코딩 검사는 유지합니다. APNG는 각 프레임을 검증하고 부가 메타데이터를 제거한 PNG로 애니메이션을 보존하며, 그 외 이미지는 WebP로 재인코딩하며 WebP의 크기 범위를 넘는 정지 이미지는 PNG로 보존합니다. 호스팅·GitHub API·실행 환경의 용량 및 메모리 제한은 별도로 적용될 수 있습니다. Worker에는 이 변경을 배포했으며 사이트·파이프라인의 변경은 아직 미배포 상태입니다. 저작권자 표시는 이미지 메타데이터에 삽입하는 워터마크가 아닙니다.

202는 **검증 대기 접수**이며 사이트 반영 완료가 아닙니다. 서버 GitHub 쓰기 권한과 실제 관리자 업로드는 실계정으로 아직 확인하지 않았습니다. API 주소 연결만으로 자동 배포가 완료됐다고 간주하지 않습니다.

기존 파일 수정·삭제나 private 원본 열람은 제공하지 않습니다. 원본·거부 파일은 삭제 후에도 private Git 이력에 남을 수 있고, 공개된 사본·다운로드는 회수할 수 없습니다. 저장소 관리자에게 원본이 보입니다.

## 자동 배포 구성과 사용자 확인

1. 앱·Worker·사진 파이프라인은 public 저장소 `main`에 반영했습니다.
2. private 저장소의 `PUBLIC_SITE_DISPATCH_TOKEN` Secret은 사용자가 등록했습니다. 토큰은 채팅이나 코드로 전달받지 않았습니다. 교체 시 public 저장소만 Contents read/write 권한을 부여합니다.
3. private 저장소의 `.github/workflows/publish.yml`과 `config/private-photos/publish.yml`의 일치 및 `PHOTO_PIPELINE_ENABLED=true`를 확인했습니다.
4. 공개용 시험 사진으로 관리자 접수 → private Actions 이미지 검증 → Pages 재빌드 → 새로고침 후 표시와 저작권자를 확인합니다.

기존 public 저장소의 `PRIVATE_ASSETS_READ_TOKEN` Secret은 private 원본 checkout용으로 유지합니다. 별도의 사진 Worker를 쓰는 구성에는 `PHOTO_GITHUB_WRITE_TOKEN`, `FIREBASE_API_KEY`, `FIREBASE_PROJECT_ID`가 필요하지만 현재 운영에서는 기존 이야기 Worker의 서버 바인딩을 사용합니다. 브라우저에는 GitHub 토큰을 반환하지 않습니다.

## 검증

- 업로드·권한 모의 테스트: 게스트, 일반 멤버 A/B, 관리자 A/B, 미검증·비활성·다른 공급자, 만료 토큰, Firestore 거절, 위험 경로·위장 MIME·과대 파일·손상 헤더·잘못된 저작권자.
- 이미지 파이프라인: 전체 디코딩, 메타데이터 제거, 큰 이미지 허용, APNG 프레임 검사, JSON 접수와 저작권자 보존, 손상 접수 거부.
- 운영 HTTP: Pages/로컬 Origin 사전 요청 204, 다른 Origin 403, 토큰 없는 업로드와 가짜 토큰 401 확인. 실사진 저장이나 브라우저 자동화는 실행하지 않았습니다.

참고: [Firebase 계정 확인 API](https://firebase.google.com/docs/reference/rest/auth), [Firebase ID token과 Firestore REST 보안 규칙](https://firebase.google.com/docs/firestore/use-rest-api).

연결 검증: [private 사진 파이프라인](https://github.com/team-kirari/kirari-private/actions/runs/44245398241), [자동 Pages 재배포 성공](https://github.com/team-kirari/kirari/actions/runs/44245434281). 대기 사진이 없는 실행으로 연결을 확인했으며 실제 로그인 사진 접수는 사용자 확인이 남아 있습니다.
